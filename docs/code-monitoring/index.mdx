# Code Monitoring

Code Monitoring searches changes in Git history and sends notifications by email, Slack, or webhook when it finds matches. Use it to watch dependency files, spot added uses of a deprecated API, or follow commits about a topic.

Code Monitoring is supported on [Enterprise](/pricing/plans/enterprise) plans.

A monitor combines a search query (the trigger) with notification destinations (actions). It observes changes after they reach Sourcegraph; it does not block commits or replace CI or an audit log.

## Watch an upstream Go-version change

Suppose you use the `sourcegraph/conc` library and want to know when an upstream change may require a Go-toolchain upgrade. Start by searching its `go.mod` history:

```sourcegraph-query
repo:^github\.com/sourcegraph/conc$ type:diff file:^go\.mod$ patternType:literal
```

This finds the [change from Go 1.19 to Go 1.20](https://github.com/sourcegraph/conc/commit/e454401b0a476b708561a7c10d4b3f268b33e604), but also dependency changes unrelated to the Go version. Narrow the query to added `go` directives:

```sourcegraph-query
repo:^github\.com/sourcegraph/conc$ type:diff file:^go\.mod$ select:commit.diff.added patternType:regexp ^go\s
```

The same commit matches on `go 1.20`. The query also finds the module's initial `go 1.19` declaration: it detects an added or replaced directive, not just version increases. It does not watch `toolchain` directives.

To follow future changes, use the refined query as a monitor's trigger on your Sourcegraph instance, with an [email, Slack, or webhook action](/code-monitoring/notifications). The repository must be available there and searchable with your permissions. The historical results above demonstrate what matches; creating a monitor records a starting revision rather than notifying you about those results.

## Choose what to watch

Triggers use `type:diff` for added or removed lines and `type:commit` for commit messages. Diff searches do not match unchanged context. Use `select:commit.diff.added` or `select:commit.diff.removed` to restrict matches to one side of a change.

### Find added uses of a deprecated API

During a migration from `ioutil.ReadFile` to `os.ReadFile`, watch for added uses of the old API:

```sourcegraph-query
repo:^github\.com/sourcegraph/src-cli$ type:diff select:commit.diff.added file:\.go$ patternType:literal ioutil.ReadFile
```

For example, [this `src-cli` commit](https://github.com/sourcegraph/src-cli/commit/e47e47de4b19079cb961b7dfc2d63755f49e0251) moves an `ioutil.ReadFile` call. It matches even though the call is both removed and added: this is not a test for a net increase. Text matches can also include comments and strings. Replace the repository and API for your migration, or use `select:commit.diff.removed` to follow removals.

### Follow CVE mentions in upstream commits

When reviewing Go upgrades, find commits whose messages mention a CVE identifier:

```sourcegraph-query
repo:^github\.com/golang/go$ type:commit patternType:regexp CVE-\d{4}-\d+
```

One result is [a `crypto/x509` change](https://github.com/golang/go/commit/7f86f957633ee31a1c17a1eb8452ca7a3d9bc141) whose message includes `Fixes CVE-2026-111943`. Any matching mention can trigger the monitor; it does not identify every security fix or determine which versions are affected.

For other patterns and filters, see [search query syntax](/code-search/queries).

## How changes are detected

Creating a monitor records the current revisions of its matching repositories. Later searches include commits reachable from the current revisions and exclude revisions already searched. A repository that enters the query's scope without a saved revision can contribute historical matches.

By default, searches use each repository's default branch, not every branch. Specify a [repository revision](/code-search/queries#repository-revisions) to watch another branch. An immutable commit or tag does not advance as commits arrive.

The default polling interval is five minutes. Repository fetches, search execution, and notification delivery add latency; there is no fixed delivery deadline. Avoid short rolling `after:` filters just to detect new commits: monitors already track revisions, and timestamp filters can exclude changes that reach Sourcegraph late.

Editing the query records a fresh starting revision. Disabling a monitor preserves its saved revisions but does not cancel queued or running work. Re-enabling resumes from those revisions, subject to the query's filters and [delivery limits](/code-monitoring/administration#limits-and-delivery).

Disabling only an action does not pause searches. Re-enabling that action does not replay notifications skipped while it was disabled.

## Choose a safe destination

Searches run with the monitor owner's repository permissions. Included results are not filtered for each email recipient, Slack member, or webhook consumer. A notification can expose code to someone who cannot open its Sourcegraph link.

Turning off **Include results** removes code excerpts, not all sensitive information. Notifications still contain the monitor name, and their search links or webhook metadata contain the query. Choose names, queries, and destinations accordingly.

See [Notifications](/code-monitoring/notifications) for destination setup and webhook payloads, or [Administration](/code-monitoring/administration) for configuration, limits, and troubleshooting.
